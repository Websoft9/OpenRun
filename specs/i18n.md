# i18n

## Scope

Two separate concerns:

- UI copy: code-owned, versioned in `src/i18n/`.
- Structured content: data-owned, stored in the database.

## UI copy

- Files: `src/i18n/en.ts`, `src/i18n/zh.ts`, `src/i18n/es.ts`, `src/i18n/fr.ts`, `src/i18n/de.ts`, `src/i18n/ja.ts`.
- Flat, namespaced keys: `nav.home`, `search.empty`.
- Access through `t(locale, key, params)`.
- No hardcoded UI strings in pages or layouts.
- No UI copy in the database.
- Format numbers and dates with `Intl` using the active locale.
- Locale comes from the URL: `/en`, `/zh`, `/es`, `/fr`, `/de`, `/ja`.
- Regional tags resolve to their base language (`es-MX` → `es`); unsupported locales fall back to English.
- Every page sets `<html lang={locale}>`.
- Missing UI messages fall back to English, so non-English catalogs may be partial.
- Run `npm run check:i18n` to verify placeholders and supported locale resolution.

## Structured content

- Facts are not translated: URLs, license, stars, language, timestamps.
- English is canonical and lives in the main tables.
- Translations live in per-locale tables:
  - `software_translations`
  - `software_analysis_translations`
  - `category_translations`
  - `tag_translations`
- Each translation row is unique by entity and locale.
- Translation rows carry `status` and `source_hash`.
- Missing or unpublished translations fall back to English.
- Git stores schema, seeds, and import/export batches, not runtime translation files.
- Search indexes include published translations.
- Never let AI overwrite fact fields.

## Rule

UI text changes with code. Catalog content changes with data. Language changes never alter facts.
